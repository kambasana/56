# Model backtest gate, 2026-10-08: FAIL

**Verdict: the model does not ship.** It does not beat the hand-weighted noisy-OR on held-out recall, and it does not beat it on the noise users would see (scan day), for the Acme repos or the hammer controls. Scoring stays on the hand-set weights. The model is not wired in.

| Gate measure | Model | Noisy-OR | Result |
|---|---|---|---|
| Held-out recall, releases both can score (100) | 16.0% | 27.0% | worse |
| Noise per Acme repo, scored at each release | 14.5 | 95.2 | better |
| Noise per Acme repo, scanned on 2026-10-07 | 14.5 | 2.17 | **worse** |
| Noise per hammer control repo, at release | 22.5 | 86.0 | better |
| Noise per hammer control repo, scan day | 22.5 | 11.0 | **worse** |

The pass rule (docs/DATA-ML.md §2.7) is strictly better on recall and on every noise viewpoint. Not Pareto-better either.

Machine-readable results: `2026-10-08-gate.json` (gate output, training metrics, other variants, reconstructed run).

## What was run

- **Data:** the audited dataset from `2026-10-08-dataset.md`, unchanged, rebuilt at commit 67a2e30. Its labels are identical to `manifest/labels.jsonl` (5,136 positives, 55 campaigns, 138,014 negatives, feature schema v3). `dataset.jsonl.gz` sha256 starts `05b2f01ca01df8c7`.
- **Split:** the dataset's time split. Cutoff 2026-01-01, and each campaign goes wholly to the side of its first release. Checked: no campaign is on both sides. Train: 119,501 rows, 1,584 positives, 25 campaigns. Test: 23,649 rows, 3,552 positives, 30 campaigns, all in 2026.
- **Features:** history only. The 18 manifest features are masked to NaN on every row, because npm unpublished 98% of the positives' manifests. `manifest` and `origin` are never inputs.
  - Scorecard, dependents and typosquat distance have no as-of history, so they are NaN everywhere.
  - Downloads are as of the release (the week ending two days before it).
- **Model:** LightGBM 4.6.0, depth 3, 7 leaves, 150 rounds, learning rate 0.05. Deterministic: one thread, seed 7.
- **Folds:** GroupKFold (5) over `group`: campaign for positives, package for negatives.
- **Variant choice:** made on out-of-fold average precision only. The rule was fixed in code before the test split was scored.

  | Variant | Out-of-fold AP | Out-of-fold ROC AUC |
  |---|---|---|
  | history + downloads, class weight (chosen) | 0.479 | 0.922 |
  | history + downloads, per-year balanced weights | 0.247 | 0.903 |
  | history only, per-year balanced weights | 0.140 | 0.882 |

- **Calibration:** isotonic, fitted on the out-of-fold predictions (88 points).
- **Threshold:** the F2-best calibrated value on out-of-fold data, 0.111.
- **Calibration caveat:** the calibrated probabilities reflect the dataset's sampled base rate (1.3% positives in train), not the real-world rate of compromised releases.
- **Parity:** the TS evaluator (`src/model/cli.ts`) against LightGBM on 25,949 rows (every test row, 2,000 training rows, 300 synthetic rows with NaNs and zeros). Max difference 0 on raw scores and 2.2e-16 on probabilities, against a 1e-6 tolerance. **Passed.**
- **Gate:** `npm run model:gate`, extended in this step:
  - the dataset's test split;
  - download series for the model's features and for the noisy-OR's established-dependency check (downloads in the week before the scoring time, as live scans use npm's last-week count);
  - the hammer controls;
  - `--no-reconstructed`.

  Scoring time is release + 1 h, which is before disclosure for every labelled release.

```
python pack/model/train.py --root . --dataset pack/model/out/dataset --out pack/model/out/model --variants
npx tsx test/model/gate.ts --bundle pack/model/out/model/model.json --cache pack/model/.cache/packuments \
  --no-reconstructed --control microsoft/TypeScript=<dir> --control mochajs/mocha=<dir> --write-requests req.jsonl
python pack/model/fetch_downloads.py --requests req.jsonl --out pack/model/.cache/downloads
npm run model:gate -- --bundle pack/model/out/model/model.json --cache pack/model/.cache/packuments \
  --downloads pack/model/.cache/downloads --dataset pack/model/out/dataset --no-reconstructed \
  --control microsoft/TypeScript=<dir> --control mochajs/mocha=<dir> --out pack/model/out/gate
```

The control directories hold `package.json` and `package-lock.json` (mocha: root, `docs/`, `repro/`), taken from raw.githubusercontent.com at the pinned commits in `test/hammer/scenarios.json`:
- microsoft/TypeScript `de61e696`

**The headline recall overstates what the model would catch first.**
- **Bursts.** Most test positives are second or later bad releases in a burst. The worm's previous release came minutes earlier: median `days_since_prev_release` is 0.02 days and median `gap_ratio` is 0.01 on unpublished positives, against 4.1 days and 1.16 on negatives. That earlier release was itself malicious.
- **First bad release per package** (the one an early warning needs): 405 of 1,142 packages flagged, **35.5%**. Later releases in a burst: 56.7% of 2,410.
- **Where npm still serves the manifest,** first-release recall is 15 of 56 (**26.8%**).

What the model learnt:
- **Cadence and popularity** decide almost everything: few releases in the past year, a short gap since the last release, and low or rising downloads.
- **Not the attack.** The publisher, install-script and dependency evidence that defines these attacks is in the masked manifest features.
- **Sampling bias.** Downloads and age carry part of the dataset's documented bias (negatives are popular lockfile packages).

- **The model's vector is stable over time,** so its count is the same at release and on scan day.
- **The noisy-OR is loud at release and quiet on scan day.** Its publisher, maintainer and young-dependency signals fade after a release, and young dependencies that have since become established (by downloads) no longer count.
- **What users see** is the scan-day view. There the model adds about 12 findings per Acme repo and 11 per control.
- **The control numbers flatter the model.** 495 of the 1,184 control packages, and 289 of their exact versions, were training negatives, because the dataset sampled negatives from the hammer lockfiles. The Acme packages were never trained on.
- **Skipped:** 6 components, all of them unpublished releases or a git dependency. The 16 replay incident releases were dropped under `--no-reconstructed` because npm serves none of their manifests.
- **Live scans** of the controls, with OSV and deps.dev, were not run. Lockfile inventories at the pinned commits, scored on the same packuments, give the noise comparison the gate needs, without network-dependent enrichers that the baseline here does not model either.

## Why it fails

1. **The signal that defines most attacks is missing for the positives.**
   - npm removed 98% of the bad releases' manifests, so publisher change, new install hook and new dependency cannot be trained.
   - What remains is cadence and popularity. That finds worm bursts, but not a single hijacked release of a normal package. The held-out releases the noisy-OR can score are mostly that kind.
2. **Recall on the test split comes mostly from worm bursts.**
   - The second and later bad releases follow the first within minutes, and `days_since_prev_release` gives them away.
   - That is real, but it is not early warning: by then the first bad release is out.
3. **The model flags quiet, low-download packages in healthy repos all the time.**
   - It has no time-decay like the noisy-OR, so on scan day it is several times noisier.
   - Part of this is the dataset's sampling bias: negatives are popular packages.

## What would change the outcome

- **Manifests for unpublished bad releases,** from a registry mirror or the replicate.npmjs.com changes feed with timestamps. The publisher, install-hook and dependency features could then be trained. This is the main blocker.
- **Score the first bad release per package only** (or weight per package), so bursts do not dominate training and evaluation.
- **Negatives sampled to match the positives' popularity and age** (for example, the same download decile and the same year), instead of only correcting by weights.
- **A noise objective in model selection,** for example the threshold chosen on a held-out set of healthy repos rather than by F2 on dataset rows.

Until then the hand-weighted noisy-OR stays.
